# Public Demo Deployment Checklist

This guide prepares Riva for a public, interactive demonstration. The repository includes a [Render Blueprint](../render.yaml) for the web app, PostgreSQL, private Redis-compatible queue, Celery worker, and Celery Beat scheduler. Creating those services requires a Render account and approval of the selected plans in the Render Dashboard. Review [current plans and pricing](https://render.com/pricing) before applying it.

## Current readiness

- [x] Docker image build definition and Compose services for Django, PostgreSQL, Redis, Celery, Celery Beat, and optional Qdrant.
- [x] Render Blueprint for a persistent full-stack demo with worker-backed features and a no-card simulated payment flow.
- [x] Health endpoint and GitHub Actions workflow for Django checks, tests, deployment checks, and image build.
- [x] Demo catalog seed command: `python manage.py seed_demo_catalog`.
- [ ] Connect the GitHub repository to Render and review/approve the Blueprint service plans.
- [ ] Let the Blueprint provision PostgreSQL, Redis-compatible queue, web, worker, and Beat.
- [ ] Confirm the generated public hostname; if adding a custom domain, set the exact host, HTTPS origin, and public URL in the web service environment.
- [ ] Decide whether to enable hosted LLM chat, semantic search, payments, email, and Telegram.
- [ ] Run the deployed-flow acceptance checklist and publish the URL.

## Stage 1: Choose the demo scope

The included Blueprint uses a demo-only simulated checkout. It never asks for card data or contacts a payment provider. The stored exchange-rate fallback is enabled only so disposable test orders can traverse the simulated checkout flow; do not use this configuration for real orders. Decide whether chat should use a real OpenAI-compatible provider. Without provider credentials, Riva provides keyword-based catalog results and clearly labeled catalog-match responses; do not describe those responses as live model-generated advice.

For semantic catalog search, provide a compatible embeddings model and a private Qdrant deployment. The included Render Blueprint omits Qdrant so the demo can start without another service; semantic search is optional and the application falls back to database keyword matching.

## Stage 2: Prepare hosting and secrets

The included Render Blueprint is the ready-to-apply reference. Its web, worker, and Beat services use paid compute plans; Postgres and Key Value use paid plans so the demo does not inherit the short lifetime, sleep, or worker limitations of free resources. Render documents that [free web services spin down after inactivity, free Postgres expires after 30 days, and free compute is unavailable for background workers](https://render.com/docs/free). Review your workspace's actual service costs before approving deployment. The Blueprint keeps Postgres and Key Value private and does not expose datastore ports.

Set deployment variables in the host's secret/configuration manager. At minimum, configure:

| Variable | Demo setting |
| --- | --- |
| `DEBUG` | `False` |
| `SECRET_KEY` | Generated by the Blueprint; never copy it into source files. |
| `ALLOWED_HOSTS` | The Blueprint reads Render's generated exact hostname. Update it if you attach a custom domain. |
| `CSRF_TRUSTED_ORIGINS` | The Blueprint reads Render's generated HTTPS origin. Update it if you attach a custom domain. |
| `SECURE_SSL_REDIRECT` | `true` when HTTPS is correctly terminated by the host/proxy. |
| `DB_ENGINE` | `postgresql` |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Unique deployment credentials. |
| `POSTGRES_HOST`, `POSTGRES_PORT` | Private host and port supplied by the database service. |
| `REDIS_URL` | Private Redis connection URL supplied by the host. |
| `TIME_ZONE` | `UTC` unless the deployment has a documented reason to select another zone. |
| `PUBLIC_SITE_URL` | Public HTTPS base URL used by the application. |
| `PAYMENT_PROVIDER` | `mock` in the demo Blueprint, with the explicit simulated checkout enabled. It is not a real payment provider. |

For a live LLM, add `LLM_BASE_URL`, `LLM_API_KEY`, and `LLM_MODEL` in Render's private environment settings after the first deployment. For semantic retrieval, also configure `EMBEDDING_MODEL`, `EMBEDDING_DIMENSION`, `QDRANT_URL`, and `QDRANT_COLLECTION`, then run `python manage.py reindex_catalog`. The demo email backend does not deliver mail, and database backup scheduling is disabled until durable object storage is configured. Never commit a filled `.env` file or put secrets in GitHub Actions logs.

## Stage 3: Deploy

1. Push the reviewed source to [the Riva AI Shop repository](https://github.com/Mhdjamadi1994/Riva_ai_shop) and confirm the [CI workflow](https://github.com/Mhdjamadi1994/Riva_ai_shop/actions) passes.
2. Open the [Render deploy flow](https://render.com/deploy?repo=https%3A%2F%2Fgithub.com%2FMhdjamadi1994%2FRiva_ai_shop), review the listed services and prices, then approve the Blueprint. Render documents [Blueprint setup](https://render.com/docs/infrastructure-as-code) and [service plans](https://render.com/pricing).
3. The web service reads its generated hostname and HTTPS origin from Render automatically. If you attach a custom domain, update `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and `PUBLIC_SITE_URL` before testing checkout.
4. Confirm web, worker, and Beat are healthy. The worker handles support drafts and queued operations; Beat triggers scheduled reports and expiry sweeps. Backup scheduling stays disabled because the blueprint does not configure durable backup storage.
5. If live LLM or semantic search is in scope, add the provider credentials and matching embedding settings via Render's secret manager, provision private Qdrant, then run `python manage.py reindex_catalog` from the service shell.
6. Create an authorized staff account from Render Shell with `python manage.py createsuperuser`. Keep its credentials private.
7. Confirm the service uses HTTPS, serves static assets, and reports healthy at `/api/health/`.

Do not copy the local Compose port bindings blindly to a public host. The supplied Compose stack binds service ports to loopback for local development; follow the chosen host's private networking and ingress instructions.

## Stage 4: Acceptance checklist

- [ ] Open the home page and verify CSS, images, navigation, and responsive layout.
- [ ] Browse and filter products; open a product detail page.
- [ ] Register a disposable account and verify sign-in and sign-out.
- [ ] Add an item to the bag and verify account-scoped checkout behavior matches the selected payment mode.
- [ ] Try recommendations and confirm the documented keyword or semantic mode is active.
- [ ] Try chat and confirm whether the response is live-provider-generated or the explicit local demo response.
- [ ] Complete a simulated checkout and confirm the sandbox clearly states that it does not collect card details or charge money.
- [ ] Submit a support ticket and verify it is visible only to the account and authorized staff.
- [ ] Check `/api/health/`, `/api/docs/`, and `/api/redoc/` according to the intended public API policy.
- [ ] Verify `/admin/` remains limited to trusted staff and no example credentials work.
- [ ] Review application, proxy, and provider logs for secrets or personal data; confirm host access-log retention settings.
- [ ] Confirm backups and recovery expectations, or disable backups if the demo has no restore plan.
- [ ] Verify support tickets are processed by the worker and remember that the included demo email backend does not deliver email.
- [ ] Capture new screenshots only with synthetic products and a dedicated demo account.

## Stage 5: Publish the URL

After all required acceptance checks pass, add the public HTTPS URL to the Live demo line in the [README](../README.md). State which features are enabled and disclose any demo limitations, such as disabled payments, seeded inventory, or local fallback chat. If the host sleeps when idle, say so beside the link.

## Values that must remain private

Never publish `.env`, database dumps, backup archives, production secrets, provider keys, webhook secrets, customer data, or screenshots containing account information. Rotate any credential that was ever committed, even if it was later removed from the current files.
